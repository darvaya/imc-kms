# Review: slice-01-credentials-login

**Reviewed:** &nbsp; · **Verdict:** block → **Resolved** (all 2 blockers, 2 important, 5 nits addressed — see [`completed.md`](./completed.md) § Review resolution)

## Summary

The slice wires a fallback email/password login that is meant to appear only when Microsoft Entra is unconfigured, and to be fully suppressed when Entra is on. The intent is right and most of the plumbing is in place, but the feature does not actually work and it does not hold its own central invariant.

Two independent blockers sink it. First, the credential login path is dead on arrival: `afterSignInHook` reads `baUser.user.*`, but the installed better-auth (1.2.8, not the 1.6.19 the task assumed) returns a flat user record from `internalAdapter.findUserById`, so the hook throws, the try/catch swallows it, `ba_session.outlineUserId` is never set, and a correct credential sign-in returns a 200 + cookie yet leaves the user unauthenticated — a silent redirect back to the login page. Second, the mutual-exclusion invariant fails open: three call sites disagree on what "Entra is configured" means (`CLIENT_ID && SECRET` vs `CLIENT_ID` alone), so a partial config (CLIENT_ID set, SECRET missing) leaves `/sign-in/email` live under a page that presents as Microsoft-only, keeping the credential endpoint — and the source-committed known password — reachable on an instance everyone believes is SSO-only. Both are grounded in the actually-installed code, not the assumed version.

Beyond those, two important issues (the same gate-disagreement surfacing in `auth.config`, and a production-safety gap in the seed script that can plant a known-password admin) and a handful of nits round out the picture. Fix the two blockers and the gate-consistency issue and the path should work; until then this cannot merge.

## Blockers

1. **`server/auth/betterAuthHooks.ts:45` — credential session is never linked; login silently fails (breaks AC4 & AC6).**
   `afterSignInHook` binds the flat user record at line 23 (`const baUser = await ctx.internalAdapter.findUserById(session.userId)`) and then reads `baUser.user.outlineUserId` at line 45 (and `baUser.user.name/email/image` at lines 79-85, 124). In the *installed* better-auth (node_modules/better-auth is **1.2.8**, not the 1.6.19 the task assumed — `package.json:118`), `internalAdapter.findUserById` returns the user record **flat** (`{ id, name, email, emailVerified, image, ... }`), not wrapped in `{ user }`. (Confirmed: `dist/shared/better-auth.XjdOGtZf.mjs:624-635` returns `user` directly; the `.d.ts` at `dist/shared/better-auth.Cl08k4BO.d.ts:144-152` shows the flat shape; by contrast `findUserByEmail` at :593 is the one that returns `{ user, accounts }`.) So `baUser.user` is `undefined` and line 45 throws `TypeError: Cannot read properties of undefined (reading 'outlineUserId')`. The outer try/catch at lines 126-131 swallows it, logs, and returns — `ba_session.outlineUserId` stays at its `null` default (`betterAuth.ts:154-161`). Downstream, `betterAuthSession.ts:44` reads `result.session.outlineUserId`, finds `null`, and returns `null`, so Koa treats the request as unauthenticated. Net user-visible effect: submit correct credentials → 200 + session cookie → UI redirects to `/` → login page just reloads, never authenticated. The mismatch is masked at compile time because `BetterAuthInstance` in `betterAuth.ts:27-36` hand-declares `findUserById` as returning `{ user: {...} }` and `betterAuth.ts:181` casts via `auth as unknown as BetterAuthInstance`; it only fails at runtime. Reproduced end-to-end against the installed package.
   **Required fix:** replace every `baUser.user.<x>` with `baUser.<x>` (lines 45, 79, 80, 81, 84, 85, 124). Correct the `BetterAuthInstance.findUserById` return type in `betterAuth.ts:27-36` to the flat shape so TypeScript catches this class of error. Add a hook unit/integration test (the slice DoD lists auth tests) asserting `outlineUserId` is set after a credential sign-in.

2. **`server/auth/betterAuth.ts:102` — mutual-exclusion invariant fails open; `/sign-in/email` stays live under a Microsoft-only page.**
   `betterAuth.ts:102-104` disables credentials only when `microsoftSsoEnabled = !!(env.MICROSOFT_CLIENT_ID && env.MICROSOFT_CLIENT_SECRET)` — it takes **both** vars to turn credentials off. Everywhere else the invariant is keyed on `CLIENT_ID` alone: `auth.ts:33-49` advertises Microsoft under `if (env.MICROSOFT_CLIENT_ID)` (email box only in the `else`), and `seed-test-admin.ts:24` refuses on `MICROSOFT_CLIENT_ID` alone. `env.ts:786-797` marks both vars `@IsOptional` with no cross-validation, and `toOptionalString` coerces an empty SECRET to `undefined`, so booting with `CLIENT_ID` set and `SECRET` empty/failed-to-inject is permitted. In that state `microsoftSsoEnabled` is false, so `socialProviders` is `undefined` (Microsoft button dead) **and** `emailAndPassword: { enabled: true, disableSignUp: true }` is active. `betterAuthHandler` is mounted unconditionally (`web.ts:72`), and better-auth 1.2.8 keeps `POST /api/better-auth/sign-in/email` live whenever `emailAndPassword.enabled` is truthy — the handler (`better-auth.DxtzDaxH.cjs:1678-1685`) throws only when `enabled` is falsy, with **no** social-provider check. So an instance the operator and `auth.config` both consider "Microsoft-only" silently accepts credential logins. `disableSignUp` blocks new accounts, but any pre-existing `ba_account` credential row still authenticates — including the source-committed seed identity `kms-test-admin@kms.local` / `KmsTestAdmin123!` (`seed-test-admin.ts:19-20`) if the DB ever ran in credentials mode before Entra was added — the exact dev→prod migration path this feature documents. This violates the spec invariant ("credentials off when Entra on"). When both vars are set (normal prod), there is no leak; the hole is strictly the CLIENT_ID-set / SECRET-missing state.
   **Required fix:** key the disable condition identically everywhere. Simplest and safest: in `env.ts` decorate `MICROSOFT_CLIENT_ID` with `@CannotUseWithout("MICROSOFT_CLIENT_SECRET")` (and vice-versa) so a partial Entra config fails validation at boot rather than fail open. Alternatively enable credentials in `betterAuth.ts` only when `!env.MICROSOFT_CLIENT_ID` (matching `auth.config` and the seed guard). Auth must fail closed.

## Important

1. **`server/routes/api/auth/auth.ts:33` — `auth.config` gates the provider on `MICROSOFT_CLIENT_ID` alone; a half-filled `.env` yields a login with no working method.**
   `auth.ts:33` branches on `if (env.MICROSOFT_CLIENT_ID)` (ID only), with the `email-better-auth` provider only in the `else if (env.BETTER_AUTH_SECRET)` branch (lines 40-49). `betterAuth.ts:102-104` gates on `CLIENT_ID && SECRET`, and `seed-test-admin.ts:24` on `CLIENT_ID` alone — three definitions of "Entra on." In the partial-config state (CLIENT_ID set, SECRET empty): `betterAuth` runs credential-only (no Microsoft social provider registered, email endpoint live), but `auth.config` advertises **only** the `microsoft-better-auth` button and hides the email/password form (it's an `else if`). Clicking "Continue with Microsoft" POSTs `/api/better-auth/sign-in/social?provider=microsoft`, which errors (no such provider configured), and the live email/password login is never surfaced; the seed also refuses. Net: a running instance with no usable UI login path. Spec Assumption 5 (`spec.md:21`), the technical note (`spec.md:68`, `!!(clientId && clientSecret)`), and AC3 (`spec.md:38`, "both client id and secret") all confirm the intended gate is ID+SECRET, so the ID-only gate is a real spec deviation, not defensive hardening. (The inverse partial state — SECRET set, ID unset — does not break, since both files land on email.) This is the UI-facing twin of Blocker 2 and should be fixed together with it.
   **Required fix:** gate the branch on `if (env.MICROSOFT_CLIENT_ID && env.MICROSOFT_CLIENT_SECRET)`. Extract a single shared `microsoftSsoEnabled` helper consumed by `betterAuth.ts`, `auth.ts`, and `seed-test-admin.ts` so the gate can never drift.

2. **`server/scripts/seed-test-admin.ts:24` — prod-safety gap: nothing enforces "dev-only" beyond the Entra check, so it can plant a known-password admin in a credentials-mode production deploy.**
   The only guard is `if (env.MICROSOFT_CLIENT_ID)` (line 24); there is no `NODE_ENV` / `ENVIRONMENT` / `isCloudHosted` / interactive-confirmation check. Because credentials mode is gated purely on Entra absence (spec Assumption 5), a production instance deployed **without** Entra runs in credentials mode — exactly the state where this guard is a no-op. `yarn seed:test-admin` then INSERTs and prints to stdout the hardcoded `kms-test-admin@kms.local` / `KmsTestAdmin123!` (lines 19-20, 96-97). As the first user of a fresh team it is provisioned `UserRole.Admin` (`betterAuthHooks.ts:36` routes `providerId === 'credential'` into `accountProvisioner`; `accountProvisioner.ts:179` sets `role: isNewTeam ? UserRole.Admin : undefined`) — a known-password admin backdoor whose credentials are in the public repo. The header comment "NEVER run against production" (line 17) is documentation only; nothing enforces it. `env.ts` already exposes `isProduction` (line 846) and `isCloudHosted` (line 835), so a guard is trivial. Exploitation requires a compound operator error (prod deploy omitting Entra + running a dev-only script + leaving the default password), which is why this is important rather than a blocker — but the impact and the standard, cheap fix keep it well above a nit.
   **Required fix:** refuse unless clearly non-production — gate on `env.ENVIRONMENT !== "production" && env.NODE_ENV !== "production"` (and/or `!env.isCloudHosted`), or require an explicit opt-in env var. Do not print the plaintext password when a non-default password was supplied via `SEED_ADMIN_PASSWORD`.

## Nits

1. **`server/scripts/seed-test-admin.ts:47` — idempotent branch silently no-ops when the `ba_user` exists without its credential `ba_account` row.**
   The re-run path keys only on the existence of a `ba_user` for the email (lines 41-45), then runs `UPDATE ba_account ... WHERE "userId" = :userId AND "providerId" = 'credential'` (lines 49-57) without capturing the affected-row count, and unconditionally logs "Updated existing credential account" (line 58) before returning. If the user row exists but its credential account row is missing (manually deleted, or the email previously logged in via a different provider), the UPDATE matches zero rows, yet the script exits 0 claiming success and no usable credential login exists — contradicting the idempotency claim in the header (line 16). *Fix:* capture the `QueryTypes.UPDATE` affected-row count; if zero, INSERT the credential `ba_account` for the existing `userId` (or upsert keyed on `(userId, providerId)`).

2. **`app/scenes/Login/components/AuthenticationProvider.tsx:124` — login error is not announced to assistive tech.**
   On a failed credential sign-in the message renders into a plain styled `<p>` (`ErrorMessage`, lines 139-144: color/text-align/font-size/margin only) with no `role="alert"` / `aria-live`. The node is conditionally mounted only on failure (`setError`, lines 96/98), so screen-reader users get no announcement that authentication failed. It is the only user-facing error channel for the credential form (no field-level error). *Fix:* add `role="alert"` (or `aria-live="assertive"`) to `ErrorMessage`.

3. **`app/scenes/Login/components/AuthenticationProvider.tsx:91` — UI treats a Better Auth 200 as full app auth; a provisioning failure yields a silent dead-end.**
   `handleSubmit` redirects to `urlWithBasePath("/")` on `response.ok` (lines 91-95), independent of provisioning. But an authenticated app session additionally requires `afterSignInHook` to set `ba_session.outlineUserId` (`spec.md:62` invariant; `plan.md` risk #3). That hook swallows errors, so on failure `response.ok` is still true, the redirect fires, `auth.info` 401s, and `Login.tsx:91` re-renders the *same* empty credential form with no error even though the credentials were correct. The client cannot cleanly distinguish this from success, so the real fix is in the hook (Blocker 1 removes the current cause), but line 91 is the surface where it manifests. *Fix:* root fix in `betterAuthHooks` (don't swallow provisioning failures); optionally surface a generic "sign-in could not be completed" notice when `auth.info` fails immediately post-login. (Title says "redirect loop"; it is actually a dead-end — the form does not auto-resubmit.)

4. **`app/scenes/Login/components/AuthenticationProvider.tsx:25` — credential form renders under the `/create` "Create a workspace" heading.**
   `AuthenticationProvider` returns `<CredentialForm/>` on `authType === "credential"` (line 25) before consulting `isCreate`, and `Login.tsx:263-276` maps providers the same way on `/create` (a reachable route via `app/routes/index.tsx:46`). Since credential sign-up is disabled (`disableSignUp: true`, `betterAuth.ts:139`), presenting an email/password box under "Create a workspace / Get started by choosing a sign-in method for your new workspace…" (`Login.tsx:223-233`) is misleading. Cosmetic only; `/create` is a secondary entry. *Fix:* suppress the credential provider when `isCreate`, or adjust the create-flow copy.

5. **`server/auth/betterAuth.ts:137` — better-auth 1.2.8 is installed, but plan/spec reason about 1.6.x.**
   The task and `plan.md:74` reason about better-auth 1.6.x toggle semantics; the installed version is **1.2.8** (`package.json:118`, `yarn.lock:10101`). The behaviors this slice relies on do hold in 1.2.8 (undefined `emailAndPassword` → `sign-in/email` throws "Email and password is not enabled"; `disableSignUp: true` → `sign-up/email` throws), so no code defect — a version-hygiene flag. *Fix:* reconcile the version referenced in spec/plan with the installed 1.2.8, or pin/upgrade deliberately and re-verify that (a) undefined `emailAndPassword` still disables the endpoint and (b) `disableSignUp` still blocks sign-up, since the mutual-exclusion guarantee depends on both.

## What was checked (dimensions) and what passed

- **End-to-end correctness of the credential login path** — Traced sign-in through better-auth 1.2.8 → `afterSignInHook` → `accountProvisioner` → `ba_session.outlineUserId` → `validateBetterAuthSession` → Koa. **Failed** (Blocker 1): the hook throws on the flat `findUserById` shape and never links the session. `getSession` was separately confirmed to return the custom `session.outlineUserId` field, so the hook is the sole break. Related gate disagreement surfaced as Important 1.
- **Security + mutual-exclusion invariant ("credentials off when Entra on")** — Checked all three gates against the installed handler behavior. **Failed** (Blocker 2): fails open in the CLIENT_ID-set / SECRET-missing state. Confirmed the both-vars-set prod path has no leak and `disableSignUp` blocks new accounts. Version semantics verified against installed 1.2.8 (Nit 5).
- **Seed script (SQL correctness, idempotency, crypto/transaction, prod-safety, admin provisioning)** — SQL, crypto (`better-auth/crypto hashPassword`), and transaction handling are sound and the fresh-DB and re-seed-after-credential-seed paths work. **Gaps:** prod-safety guard (Important 2) and the half-seeded idempotency no-op (Nit 1).
- **Sub-path safety + login UI integration** — `urlWithBasePath` is used for the post-login redirect, so BASE_PATH is honored. Provider rendering in `Login.tsx` is correct for the single-credential case. **Gaps:** error accessibility (Nit 2), 200-treated-as-auth dead-end (Nit 3), and the `/create` heading incongruity (Nit 4).
- **Guard relaxation review** — The removed hard throw in `betterAuth.ts` and the relaxed `betterAuthSession.ts` guard (no longer requiring `MICROSOFT_CLIENT_ID`) are consistent with the credentials-mode design; no defect found there beyond the gate-disagreement already captured in Blocker 2.
